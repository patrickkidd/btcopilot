The review's tables, laid over what exists

Every row below says what it reuses. Teal = an existing table, type or enum used as it is. Amber = new. Ids are the existing integer primary keys with created_at and updated_at from the shared model base; timestamps are DateTime; JSON columns are JSONB with the SQLite variant, the way the change log already does it.

Things that are not tables on purpose

The next meeting's agenda is a query, not a table: rules with a flag set, review items still unresolved, codings without Done. Closing an item is clearing the flag, settling the item, or pressing Done.

The guidelines file in the repository is generated from the rules table on every ratification, never edited by hand, as ruled.

The ground-truth export the harness reads is generated from the case diagrams' ratified items, in the shape the batch harness already reads.

Three choices worth your eye. A coding is a diagram row, so coders use the app's own editors and picture and nothing new stores an event. A settle is a change row on the case's diagram, so ratification has the same audit trail as every other edit. The agenda is derived, so there is nothing to keep in sync.
