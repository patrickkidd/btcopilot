## 1. Ten pytest failures, one cause, currently on the branch

All ten are `btcopilot/tests/pro/test_modelmixin.py`. The family-switcher commit added
`users.current_diagram_id`, so `User.as_dict()` now returns one more key and the ten
expected dictionaries were not updated.

```
E   AssertionError: assert {'active': Tr...d': None, ...} == {'active': Tr...ame': '', ...}
E     Left contains 1 more item:
E     {'current_diagram_id': None}
btcopilot/tests/pro/test_modelmixin.py:34
```

Stale expectations, not broken behaviour. Worth one note beyond the fix: the new key
rides in `User.as_dict()`, which is the payload the Pro and Personal desktop apps
receive, so those clients now get a field they have never seen.

## 2. Every desktop golden is stale or missing

All 19 visual failures are the desktop project, and none of them is a rendering defect
the images caught. Two causes:

- **Stale baselines.** The desktop goldens were recorded against a **458px** frame. The
  page now renders **838px** there, because `web/src/theme.css` gained
  `@media (min-width: 900px) { .app { max-width: 840px } }`. Fifteen tests fail on the
  size mismatch alone: `Expected an image 458px by 187px, received 838px by 155px`.
  Affected: picture (4), moves (3), chat (1), scroll (2), sessions/settings/menu (5).
- **Missing baselines.** The four new `board.spec.ts` tests have no desktop snapshot at
  all: `A snapshot doesn't exist at …/board-first-move-desktop-darwin.png`.

The practical consequence: **desktop is currently unverified by the golden suite.** The
frame width itself is the row UI_GAP already marks NEEDS-OWNER, so re-recording the
desktop goldens should wait on the owner ruling that number.

One of the nineteen is a different bug: `layout.spec.ts:83` asserts
`strip.overflows === true`, which is true only at 390px ("three controls at 390px do not
fit side by side"). It runs in both projects and can never pass on desktop.

## 3. Layout — the owner's red line

The standard: "chat bubbles must never change position on screen just from a click on a
chip", and the suite's own heading, "the board is the only thing that resizes the picture".

| # | element | spec | measured |
|---|---|---|---|
| 3a | a tap on a **chapter mark** | the picture keeps its height, the chat below does not move | the picture grows **154.59 → 234.59px (+80px)**, the caption drops **149.59 → 229.59**, the chat top drops **198.59 → 278.59**, every bubble moves down exactly **80px**. Fixtures `one`, `three40`, `dense60`, `hostile`, at **both** 390×844 and 1280×800 |
| 3b | a tap on the **last zone**, phone, `moves` | same | picture **234.59 → 250.19px**, bubbles down **15.6px**. Phone only |
| 3c | a tap on an **offered chip** | the chip goes into the composer, nothing moves | the chat loses **4px** of height and both bubbles move **up 21px** on a phone. Desktop shows the height change without the bubble move |
| 3d | a tap on the **shelf**, desktop, `empty` | nothing moves | everything shifts **left 2px** as a scrollbar appears |

Why the suite misses 3a: every assertion in `layout.spec.ts` uses the `moves` fixture and
taps `data-target="zone"`. The `moves` picture already sits at the taller level, so its
zone taps genuinely move nothing. No layout test covers a chapter tap and no layout test
uses any other fixture.

`web/src/picture.ts` says in a comment that the chat "only ever moves on a deliberate
level change and never on a tap". A chapter tap **is** a level change under that reading,
so this may be intended. It still contradicts the second half of the ratified standard,
and it is the most common first interaction on a fresh record.
**This wants the owner's ruling, not a fix an agent picks.**
EVIDENCE: `verify_layout_probe.json`, `gate_phone_three40.png`.

## Not a product defect — recorded so nobody re-chases it

An earlier golden run produced 23 failures. Cause: the visual suite keeps its saved
sign-ins in one shared directory inside the checkout, `web/tests/visual/.auth`, and takes
an exclusive lock so two runs cannot overwrite each other. This verifier deleted that lock
at the start of the session. Another agent's run then rewrote the shared sign-ins with
cookies for a different database, and every test after 20:19 signed in as nobody and got a
redirect to the login page. The lock works; deleting it is what broke the run. EVIDENCE:
`verify_server.log` shows `GET /companion/` flipping from 200 to 302 at 20:19:04. Later
runs used sign-ins written to this job's own directory and left the lock alone.
