## What actually fails

1. **The sessions button is on every screen in the code but visible on none of them but the chat.**
   The screen switch explicitly un-hides it for every screen, yet it lives inside the chat screen's
   input bar, so when any other screen is up its parent is hidden and the button measures zero by
   zero. A coder who lands on the one task card, and Patrick on the table, the ballot or the meeting,
   has no sessions button to tap. The back arrow at the top left does return to the chat, so nothing
   is permanently unreachable, but the drawn route is not there. Seen on all three browsers.

2. **A coder with nothing to do loses the way to everything they have finished.** When the tasks
   endpoint answers with no open task, the app never opens the one task card and the sessions sheet
   hides its task button. The finished-task record, and through it the result of the last meeting,
   is then unreachable from the browser even though the data is there. This is the state every coder
   is in between a ratification and the next conversation Patrick puts on the table.

3. **The coding guidelines have exactly one door, and it is shut between meetings.** The guidelines
   are read from the (i) at the top of the coding screen, and the coding screen only opens from an
   open task. So in the window right after a meeting, when the guidelines have just changed, nobody
   can read them. The spec says anyone can read the current guidelines inside the app.

4. **Ratifying takes eleven seconds and says nothing while it works.** The tap sends one request
   that writes the guideline changes with two model calls. The button keeps reading "ratify", no
   progress is shown, and nothing stops a second tap. Measured at 11 seconds on all three browsers
   and 11 to 12 seconds in the server log across four runs.

5. **The ballot shows how many coders backed each take.** Each take reads "2 coders" beside it while
   the vote is open. The spec puts names and counts at the meeting, for the first time, so that
   nobody defers to the room. The takes themselves are correctly unnamed.

6. **Coders appear under two different names in the same list.** The meeting shows `ballot1` and
   `ballot3` as raw sign-in names beside `Z.Ǆ.` as initials, and the table screen shows
   `patrickkidd+beta` in full beside `S.A.` and `L.W.`. Whoever has a first and last name gets
   initials; whoever does not gets their email address.

7. **Two ballot controls drawn are not there.** There is no count of coders who left an item out,
   and no place to say why you voted as you did. Both lines are tagged drawn rather than built in
   the spec, so this is a gap against the drawing, not a regression.

## Everything that passed

The table screen, the ballot, the meeting, ratification and the result screen are otherwise whole,
and identical across Chromium and WebKit at phone width and Chromium at desktop width. No console
error, no failed request, no horizontal scroll and no element past the edge was seen on any screen
in any browser. The result screen after a real ratification carries the ratified and unresolved
counts, agreement before and after side by side, the coach's pass against the agreed record, the
rules the AI wrote each with the item and margin it came from and a flag link, where the AI differed
from the room, and what each coder tends to do. The word gold appears nowhere.

## Deviation: ratifying still takes eleven seconds

The brief offered moving the rule drafting to a background task, the way the coach's replay runs.
It was not done. The replay is registered as a background task but no worker runs against the
sandbox, so moving the drafting there would leave the result screen with no guideline changes on
it — breaking a check that passes today, on the screen Patrick is about to walk. The work stays in
the request and the screen now says it is working. Moving it later needs a worker in the sandbox
first.

## One question this raised

A professional signing in lands on a coding task card, not on their chat, because every subscriber
is offered whatever is on the table. That follows the rule that nobody is assigned and any coder may
code any conversation, but it may not be what is wanted for someone who is only a clinician. Not
changed; it needs a ruling.
